발표에서 k6 부하테스트 데모에 쓸 "트래픽이 몰리는 상황" 시나리오를 논의함 (2026-06-08). 사용자가 실제 이커머스 운영 관점에서 시나리오를 뽑아 k6 시연에 활용할 예정이라고 밝힘.

## 우리 기능과 직결되는 후보 (가장 유력)
1. **할인 이벤트 오픈 시점 동시 접속** — 정시 할인 오픈에 다수가 같은 카테고리/할인 페이지 조회 → `product` 서비스 + MongoDB 부하
2. **회원가입 러시 + 포인트 지급** — 가입 시 포인트 지급 이벤트로 가입 요청 몰림 → `auth-member` + MariaDB 쓰기 부하
3. **인기 상품 페이지 쏠림** — 특정 상품 하나에 조회 집중 (캐시 부재 시 DB 직격 — Redis 활용 포인트와 연결 가능)
4. **포인트 차감(결제 시뮬레이션) 동시 요청** — 다수가 같은 상품을 동시에 "구매"하며 포인트 차감 트랜잭션 몰림 (동시성/정합성 이슈 시연에 적합)

## 일반 이커머스 패턴 (참고용, 우선순위 낮음)
5. 타임딜/선착순 쿠폰, 6. 푸시 알림 발송 직후, 7. 그로서리 특성상 저녁 주문 집중(샛별배송 마감 전)

**Why**: 사용자가 "k6 시연용으로 쓸 트래픽 쏠림 시나리오"를 정리해달라고 요청. 단순 일반론보다 우리 아키텍처(MongoDB/MariaDB 분리, 포인트 시스템, [[architecture-decisions]])와 바로 연결되는 시나리오가 "왜 이 구조로 설계했는가"를 보여주는 발표 스토리로 이어짐.

**How to apply**: k6 스크립트나 부하테스트 관련 작업을 할 때 1번(할인 이벤트 오픈) 또는 4번(포인트 차감 동시 요청)을 우선 후보로 제안할 것 — "동시에 같은 자원에 접근"이라는 부하테스트 핵심을 보여주면서 우리 설계 의도와도 맞물림. 아직 최종 선택은 안 됐으므로, 작업 시작 시 사용자에게 확정 여부를 다시 확인할 것.
