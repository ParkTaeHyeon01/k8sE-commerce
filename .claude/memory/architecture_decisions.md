사용자가 확정한 백엔드 아키텍처 방향 (2026-06-08 결정):

## MSA + gRPC 구조
- 서비스 간 통신: **gRPC**
- 프론트엔드에는 **게이트웨이(BFF)가 JSON으로 변환**해서 제공 (프론트는 gRPC를 직접 알 필요 없음)
- 서비스는 최소 단위로 분리 (절충안): `auth-member`(인증+회원+포인트 통합), `product`(크롤링 데이터), `gateway`(BFF)

## 인증/회원
- **OAuth**: 구글(Google) 1개만 "보여주기 식"으로 구현 (이유: 설정·예제가 풍부해 구현 리스크가 낮음. 네이버도 후보였으나 Google로 결정)
- **자체 회원가입**: 아이디/비밀번호 방식 추가 구현

## DB 역할 분리 (polyglot persistence)
- **MariaDB**: 회원 정보, 인증, 포인트 — 정합성/트랜잭션이 중요한 정형 데이터 (RDBMS 적합)
- **MongoDB**: 크롤링 상품 데이터 — 카테고리별로 필드가 조금씩 달라 스키마가 유동적 (Document DB 적합)
- 이유가 명확한 기술 선택이라 발표 시연("왜 두 DB를 쓰는가")에서도 설득력 있음

## 결제 대체 (포인트 시스템)
- 실제 결제 연동은 어려우므로 **회원가입 시 고정 포인트 지급 → 포인트 차감으로 "결제" 시뮬레이션**
- 최소 기능만: 가입 시 고정값 지급 + 단순 차감 (복잡한 결제 로직 없음)

**Why**: 강사 지침("애플리케이션 개발은 최소, API 보여주기 식")과 [[project-scope-and-role]]의 "데모에서 안정적으로 흐름을 보여줄 수 있는 최소 구성" 원칙을 유지하면서도, MSA+gRPC 구조는 k8s/ArgoCD로 여러 서비스를 독립 배포하는 모습을 보여주기에 적합하다고 판단해 채택함.

**How to apply**: 백엔드 서비스 설계·구현 시 이 3개 서비스 분리 구조와 gRPC 통신 방식을 기준으로 진행. 각 서비스 기능은 항상 "최소/보여주기 식" 범위를 유지하고 추가 기능 제안을 자제할 것.
